# ССК «Ладья» — ТюмГУ

Сайт спортивного клуба: расписание секций, соревнования, индивидуальные и
командные заявки, админка и выгрузка участников в Excel.
Стек: Python 3.12, FastAPI, Jinja2, SQLAlchemy, PostgreSQL 17, Alembic, SQLAdmin.

## Что где находится

| Путь | Назначение |
| --- | --- |
| `app/main.py` | Сборка приложения, роутеров, админки и middleware |
| `app/routers/` | HTML-страницы и приём форм |
| `app/api/` | JSON API; `/api/v1/health` — доступность процесса, не проверка БД |
| `app/services/` | Правила заявок, серверная CAPTCHA, формирование Excel |
| `app/models/`, `app/schemas/` | Таблицы БД и проверка входных данных |
| `app/db/` | Подключение к БД, фабрика сессий и зависимости |
| `app/admin/` | Админка, вход, CSRF и политика ограничения входа |
| `app/core/` | Конфигурация, CSP/заголовки, лимиты, время, branding и согласия |
| `app/templates/`, `app/static/` | Шаблоны, CSS, JS и изображения |
| `app/documents/` | Два обычных UTF-8 текста: согласие и политика |
| `app/cli/create_admin.py` | Разовое создание администратора с интерактивным паролем |
| `migrations/`, `alembic.ini` | История изменений БД; не удалять при передаче |
| `tests/` | Безопасность и критические сценарии; не входят в образ |
| `scripts/check_deployment.py` | Ручная проверка production-настроек без секретов и соединения с БД |
| `deploy/` | Шаблон production-окружения и конфигурация Caddy/HTTPS |
| `Dockerfile`, `docker-compose.yml` | Production-образ и единственный Compose для сервера |

HTML формируется на сервере. Роутеры обращаются к сервисам и БД, шаблоны только
показывают данные. Синхронные операции БД выполняются вне event loop; сессия не
удерживается во время запроса CAPTCHA. Отдельный слой repositories не нужен
для текущего размера приложения.

## Реализованные механизмы

1. Серверная проверка заявок: тип регистрации, университетский домен почты,
   повторные почты участников, срок подачи и открытость регистрации.
   Неопубликованные соревнования недоступны для просмотра и отправки заявок.
2. Правила команд: название проверяется на уникальность внутри соревнования
   без учёта регистра; минимум и максимум участников обязательны и проверяются
   при создании соревнования и отправке заявки.
3. Автоматические slug: адреса видов спорта и соревнований формируются из
   названия, при совпадении добавляется числовой суффикс.
4. Защита админки: пароли хешируются Argon2, изменяющие запросы защищены CSRF,
   выход выполняется через POST. Сессионные cookie имеют HttpOnly/SameSite=Lax,
   в production также Secure; включены HTTPS-перенаправление и проверка Host.
5. Ограничение запросов: отдельные лимиты входа по логину и IP, общих запросов
   и отправок заявок. Счётчики хранятся в PostgreSQL и разделяются между процессами;
   при превышении возвращаются 429 и Retry-After.
6. Серверная SmartCaptcha: отправка заявки блокируется без корректного токена,
   при отсутствии настроек или недоступности сервиса проверки.
7. Заголовки безопасности: CSP, HSTS для HTTPS в production, X-Content-Type-Options,
   X-Frame-Options, Referrer-Policy и Permissions-Policy. Для CAPTCHA предусмотрен
   проверочный режим CSP с последующим переключением на принудительный.
8. Согласия: страницы читают обычные UTF-8 тексты из `app/documents/`, выводят их
   с экранированием и сохранением переносов. Заявка хранит дату, снимок текста
   и автоматически вычисленный идентификатор. Изменение согласия требует повторного
   подтверждения; текст перепроверяется после CAPTCHA. Ручных номеров версий нет.
9. Работа с БД: синхронные операции выполняются в рабочих потоках, сессии закрываются
   внутри них. Во время проверки CAPTCHA соединение не удерживается; перед сохранением
   заново проверяются публикация и параметры соревнования, при ошибке транзакция откатывается.
10. Единое время: даты со временем хранятся в UTC, а админка, публичные страницы
    и Excel используют `APP_TIMEZONE` — по умолчанию Тюмень, UTC+5.
11. Выгрузка Excel: доступна администратору для одного соревнования, содержит
    строку на каждого участника, шапку соревнования и объединённые ячейки команды.
12. Брендинг: пути логотипов, фонового изображения и favicon собраны
    в `app/core/branding.py`.
13. Production-развёртывание: многоэтапный Docker-образ без dev-зависимостей,
    запуск приложения без root, закрытые порты приложения/БД и Caddy перед приложением.
    Настройки передаются через `.env`; перед запуском проверяется production-конфигурация.

## Локальный запуск и проверки

Скопируйте `.env.example` в `.env`, укажите подключение к отдельно запущенной
локальной PostgreSQL в `DATABASE_URL`. Для локальной работы без CAPTCHA явно
задайте `CAPTCHA_ENABLED=false`. Секреты не коммитить.
Compose в репозитории предназначен только для production.

```sh
poetry install --no-root
poetry run alembic upgrade head
poetry run python -m app.cli.create_admin --login admin
poetry run uvicorn app.main:app --reload
poetry run pytest -q
poetry run ruff check .
```

Адрес: `http://localhost:8000`. Для браузерной проверки CSP установите Chrome и задайте
`RUN_CSP_BROWSER=1` (при необходимости `CHROME_BIN` — путь к браузеру).
Тесты используют отдельную SQLite, а не рабочую PostgreSQL.

Для production используется тот же путь `.env`, но шаблон
`deploy/production.env.example`. Compose автоматически читает этот файл из
корня проекта через `env_file: .env` для всех трёх сервисов, включая секреты;
передавать `--env-file` не нужно. Все параметры приложения перечислены в шаблоне.
Настройки локальной разработки и production не смешивайте: внутри Docker хост
БД — `postgres`, а `PRODUCTION=true`.
Порядок production-развёртывания: [DEPLOYMENT.md](DEPLOYMENT.md).
