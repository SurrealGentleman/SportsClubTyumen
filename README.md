# Спортивный клуб ТюмГУ

Монолитное FastAPI-приложение для расписания тренировок, публикации соревнований
и приёма заявок студентов ТюмГУ. Реализованы backend-каркас, конфигурация
PostgreSQL, модели SQLAlchemy, Alembic, Docker Compose и защищённая панель SQLAdmin.

## Стек

- Python 3.12+
- FastAPI
- PostgreSQL и psycopg 3
- SQLAlchemy 2.x
- Alembic
- SQLAdmin
- Poetry
- Docker Compose

## Подготовка окружения

```powershell
Copy-Item .env.example .env
poetry install --no-root
```

Перед использованием вне локальной разработки замените `POSTGRES_PASSWORD` и
`SECRET_KEY` в `.env`.

## Локальный запуск

Запустите PostgreSQL:

```powershell
docker compose up -d postgres
```

Примените миграции и запустите приложение:

```powershell
poetry run alembic upgrade head
poetry run uvicorn app.main:app --reload
```

Health endpoint: `GET http://localhost:8000/api/v1/health`.

JSON-маршруты находятся в `app/api/health.py` и объединяются в
`app/api/router.py`. Префикс `/api/v1` задаётся при подключении роутера в
`app/main.py`, без дополнительных папок версий. Общая зависимость сессии БД
(`get_db` и `SessionDep`) находится в `app/db/dependencies.py` и используется
как публичными страницами, так и тестами.

Фабрика сессий привязана к конкретному приложению через
`app.state.session_factory` и доступна как `SessionFactoryDep`. Асинхронная
отправка заявки читает форму, а синхронную обработку запускает в threadpool:
сессии создаются и закрываются внутри рабочих функций, не передаются между
асинхронными вызовами. Во время проверки CAPTCHA соединение БД не удерживается;
перед сохранением настройки соревнования перечитываются. Проверка входа,
счётчики панели администратора и сборка Excel также выполняются в рабочих потоках.

## Публичные страницы

- `/` — главная страница клуба;
- `/schedule` — активные спортивные направления;
- `/sports/{slug}` — расписание выбранной секции;
- `/competitions` — опубликованные соревнования;
- `/competitions/{slug}` — информация о соревновании.
- `/competitions/{slug}/register` — индивидуальная или командная заявка.

Страницы формируются на сервере через Jinja2, используют Bootstrap 5 и получают
расписание и соревнования из базы данных. Наполнение создаётся через `/admin`.

Публичные маршруты разделены в `app/routers/` на `home.py`, `schedule.py`,
`competitions.py`, `registrations.py` и `legal.py`; общий роутер собирается в
`app/routers/__init__.py`. Общий поиск соревнований и проверки для отображения
находятся в `_competition_helpers.py`. Настройка Jinja2, фильтры дат и глобальные
переменные шаблонов централизованы в `app/core/templating.py` и не зависят от
регистрации маршрутов. Бизнес-логика заявок остаётся в `app/services/registrations.py`.

## Административная панель

После применения миграций создайте первого администратора. Пароль запрашивается
интерактивно и не сохраняется в истории терминала:

```powershell
poetry run python -m app.cli.create_admin --login admin
```

Панель доступна по адресу `http://localhost:8000/admin`. В ней можно управлять
видами спорта, тренировками, соревнованиями, заявками и участниками заявок.
В списке соревнований выберите одну строку и нажмите «Выгрузить заявки в Excel».
Файл содержит отдельную строку для каждого участника команды; для индивидуальной
заявки поле «Команда» остаётся пустым. Название и параметры соревнования вынесены
в шапку отчёта, а общие ячейки командной заявки объединяются на все строки её
участников.

Slug вида спорта и соревнования создаётся автоматически из названия. При
совпадении к адресу добавляется числовой суффикс. Название команды уникально в
рамках одного соревнования без учёта регистра букв.

Все даты со временем хранятся в PostgreSQL как точные моменты времени в UTC.
Админка, публичные страницы и Excel-файлы вводят и показывают их в часовом поясе
Тюмени `Asia/Yekaterinburg` (UTC+5). Его можно изменить через `APP_TIMEZONE`.

Для production-развёртывания с HTTPS установите в `.env`:

```env
SESSION_COOKIE_SECURE=true
```

## Запуск через Docker Compose

```powershell
docker compose up --build
```

Сервис `app` ожидает готовности `postgres`, применяет миграции и запускает Uvicorn
на `http://localhost:8000`.

## Проверки

Общие тестовые данные создаются функциями из `tests/factories.py`, HTTP-вход и
CSRF-помощники находятся в `tests/admin_helpers.py`, общие фикстуры — в
`tests/conftest.py`. Тестовые модули не импортируют друг друга. Специализированные
наборы данных и функции, нужные только одному сценарию, остаются рядом с ним.
Тестовое приложение получает свою фабрику сессий через `create_app`, без
дублирующего переопределения зависимости БД в общей фикстуре.

```powershell
poetry run pytest
poetry run ruff check .
poetry run ruff format . --check
poetry run alembic upgrade head --sql
docker compose config --quiet
```

## Модели первого этапа

- `Sport` — вид спорта;
- `Training` — тренировка и её группа;
- `Competition` — соревнование с индивидуальной или командной регистрацией;
- `Registration` — заявка;
- `RegistrationMember` — участник заявки;
- `Admin` — администратор с хешем пароля.

Публичные пользовательские аккаунты и OAuth не используются. Дополнительная
полировка интерфейса относится к следующему этапу.

## Согласие на обработку персональных данных

В индивидуальной и командной регистрации обязательны отдельные галочки согласия.
Командная форма дополнительно требует подтверждения капитана о получении согласий
каждого участника. Это подтверждение не заменяет документы участников: организатор
получает и проверяет их отдельно.

Согласие доступно по `/legal/personal-data-consent`, политика — по
`/legal/privacy-policy`. Сейчас обе страницы содержат только заголовки.
Старая ссылка скачивания перенаправляет на страницу согласия.

Текущий шаблон согласия указан в `app/core/privacy.py`; для политики используется
`app/templates/legal/privacy_policy.html`. Предыдущий проект текста согласия
сохранён в `app/templates/legal/documents/personal_data_consent_v1.html`.

При изменении текста или реквизитов обновляйте `CONSENT_VERSION` и имя шаблона
в `app/core/privacy.py`, сохраняя предыдущие версии документов. Для каждой новой
заявки сохраняются дата согласия (UTC), версия и точная копия его текста.
Старым заявкам согласие задним числом не присваивается.

Перед запуском обновлённого приложения выполните `poetry run alembic upgrade head`.
Миграция добавляет только nullable-поля, не изменяя существующие заявки.

## CAPTCHA и проверка безопасности

Общий механизм счётчиков `DatabaseRateLimiter` находится в
`app/core/rate_limit.py`: он не зависит от админки и получает таблицу счётчиков
явно. `app/admin/rate_limit.py` содержит только политику входа по IP и логину,
а `app/core/http_security.py` — политику общих запросов и отправки заявок.
Формат ключей, таблицы и настройки лимитов при разделении не изменялись.

Заголовки безопасности и проверка CSP:
[docs/security-headers-2026-10-26.md](docs/security-headers-2026-10-26.md).
Обычные страницы и админка используют принудительную CSP; для настроенного
SmartCaptcha-виджета до проверки с рабочими ключами действует проверочный режим.

Настройка текущего Render и последующего переноса владельцам:
[docs/deployment-security.md](docs/deployment-security.md).
На Render HTTPS/Secure-cookie включаются автоматически; для полного production
нужно создать SmartCaptcha и заполнить Environment по инструкции.
Перед запуском новой версии примените миграции: `poetry run alembic upgrade head`.

Выводы аудита и оставшиеся риски: [docs/security-audit-2026-10-20.md](docs/security-audit-2026-10-20.md).
Первый шаг исправлений (лимиты входа, CSRF админки и POST-выход):
[docs/security-hardening-step1-2026-10-20.md](docs/security-hardening-step1-2026-10-20.md).
Перед запуском примените новую таблицу счётчиков: `poetry run alembic upgrade head`.
Повторить локальный аудит без изменения рабочей БД:
`poetry run python -m scripts.security_audit`.

Для заявок включена серверная проверка Яндекс SmartCaptcha. Настройте в `.env`
или переменных окружения хостинга `SMARTCAPTCHA_CLIENT_KEY`,
`SMARTCAPTCHA_SERVER_KEY`, `SMARTCAPTCHA_ALLOWED_HOSTS` и оставьте
`CAPTCHA_ENABLED=true`. Хосты указываются через запятую без схемы и пути,
например `example.ru,www.example.ru`; для локального нестандартного порта —
`localhost:8000`. Такие же домены нужно разрешить в настройках капчи Yandex Cloud.

Без ключей/хостов или при недоступности проверки отправка заявок блокируется.
Для локальной разработки без сервиса можно явно установить `CAPTCHA_ENABLED=false`.
Серверный ключ не публикуйте и не добавляйте в Git. После изменения окружения
перезапустите приложение. Новые сторонние Python-зависимости не требуются.
