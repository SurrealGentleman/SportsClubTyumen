## Render: что уже делает приложение

При `RENDER=true` приложение автоматически использует `RENDER_EXTERNAL_URL`,
включает Secure для сессионной cookie, HTTPS-redirect, HSTS на HTTPS-ответах
(`max-age=31536000`, без includeSubDomains/preload) и проверку Host.
Cookie сохраняет HttpOnly и SameSite=Lax. Локальная разработка остаётся HTTP.
`PUBLIC_BASE_URL`, если задан, имеет приоритет над URL Render. Пока своего домена
нет, используется существующий адрес `имя-сервиса.onrender.com`.

Render сам выпускает TLS-сертификат, завершает TLS на своём балансировщике
и перенаправляет входящий HTTP на HTTPS. Внутри до Uvicorn используется HTTP:
правильные forwarded-заголовки нужны для схемы URL, CSRF и IP-лимитов.

Для сервиса с runtime **Python 3**:

Build Command:

```sh
poetry install --only main --no-root && poetry run alembic upgrade head
```

Start Command:

```sh
poetry run uvicorn app.main:app --host 0.0.0.0 --port "$PORT" --proxy-headers
```

Python-runtime Render сам задаёт `FORWARDED_ALLOW_IPS=*`. Это настройка для его
балансировщика, не рекомендация для произвольного VPS. Для Docker-runtime нужно
настроить доверие proxy отдельно; указанная выше команда относится к Python 3.
Если тариф поддерживает pre-deploy command, миграцию удобнее вынести туда.
Health Check Path: `/api/v1/health`. Не отключайте rate limit для произвольных путей.

## Создать и подключить настоящую капчу

1. Откройте [создание капчи в Yandex Cloud](https://yandex.cloud/ru/docs/smartcaptcha/operations/create-captcha).
   Создайте капчу для текущего хоста `имя-сервиса.onrender.com`, без `https://`
   и пути. Не отключайте проверку доменов. Отдельный купленный домен не требуется.
2. Скопируйте клиентский и серверный ключи из настроек созданной капчи.
   Клиентский начинается с `ysc1_`, серверный — с `ysc2_`.
3. В Render → сервис → Environment внесите значения из
   [шаблона](../deploy/production.env.example), заменив все заглушки.
   `SMARTCAPTCHA_ALLOWED_HOSTS` должен содержать точный текущий хост.
   `PUBLIC_BASE_URL` можно не задавать до появления своего домена.
4. Сохраните существующие `DATABASE_URL` и уникальный `SECRET_KEY` (от 32 символов).
   Не меняйте секрет без необходимости: это завершит текущие сессии.
5. После заполнения ключей включите `PRODUCTION=true`, `APP_DEBUG=false`,
   `DATABASE_ECHO=false`, `CAPTCHA_ENABLED=true`. Выполните Save and deploy.

До создания ключей не включайте `PRODUCTION=true`: приложение намеренно
не запустится с неполной production-конфигурацией. На Render HTTPS/Secure-cookie
работают и без этого флага, но формы при включённой капче без ключей заблокированы.
Не отключайте CAPTCHA для обхода этого ограничения на публичном сайте.

Серверный ключ вводится только в Environment/секретное хранилище, не в Git и не
в переписку. Клиентский ключ доступен браузеру по назначению.

## Лимиты

- `REQUEST_LIMIT_PER_MINUTE=120`: динамические HTTP-запросы с одного IP, включая админку.
- `REGISTRATION_LIMIT_PER_MINUTE=10`: отправки форм соревнований с одного IP,
  независимо от соревнования, результата валидации и решения CAPTCHA.
- Вход дополнительно ограничен прежними 5 попытками на логин и 30 на IP за 15 минут.

Лимиты — фиксированные окна с первой попытки, не скользящая минута. При исчерпании
возвращаются 429, русское сообщение и `Retry-After`. Запросы блокируются до разбора
формы, обращения к SmartCaptcha и создания заявки. Данные сохраняются в общей БД
и не сбрасываются сменой cookie или перезапуском worker. IP/логины хранятся как HMAC.
Общие счётчики используют новую таблицу `request_limits`, отдельно от
`admin_login_attempts`, чтобы минутная очистка не сбрасывала ограничения входа.
Health check и статические ресурсы исключены. Для вуза с общим NAT при необходимости
увеличьте лимиты после оценки реального трафика. Это не замена защите от DDoS
на балансировщике/WAF.

## Миграция и проверка

Перед запуском необходима миграция `20261025_06`:

```sh
poetry run alembic upgrade head
poetry run python -m scripts.check_deployment
```

Вторая команда не выводит секреты и не подключается к БД. Код 0 означает полную
конфигурацию production, но не проверяет валидность ключей у Yandex и сертификат.
После развёртывания проверьте в браузере:

1. HTTP перенаправляется на HTTPS; сертификат действителен.
2. Вход в админку работает, cookie `session` имеет Secure/HttpOnly/SameSite=Lax.
3. Виджет капчи загружается, настоящая заявка после прохождения сохраняется.
4. Без токена капчи, с неправильным/повторным токеном заявка не сохраняется.
5. В ответах HTTPS есть HSTS; при превышении лимита — 429 и `Retry-After`.

Не проверяйте нагрузку на рабочем сайте: для этого есть изолированные автотесты.

Проверки кода 25 октября: **176 тестов пройдено**, Ruff и проверка форматирования
успешны; конфигурация Docker Compose и генерация SQL миграции для PostgreSQL
проверены. Миграция в рабочую БД не применялась. Тесты используют SQLite и
подменённые ответы CAPTCHA, не подтверждают реальную выдачу сертификата,
работоспособность ещё не созданных ключей и настройки Render Dashboard.

## Передача владельцам

Новые владельцы настраивают DNS и TLS-сертификат на своём reverse proxy,
закрывают прямой внешний доступ к порту приложения и БД. На сервере задают:
`PRODUCTION=true`, `PUBLIC_BASE_URL=https://новый-домен`, разрешённые хосты капчи,
рабочие ключи своей капчи и свой `SECRET_KEY`. `RENDER` не задают.
Пример Uvicorn за локальным proxy:

```sh
uvicorn app.main:app --host 127.0.0.1 --port 8000 --proxy-headers --forwarded-allow-ips=127.0.0.1
```

Для Docker вместо loopback указывают адрес/сеть доверенного proxy и исключают
публичный доступ к backend. `*` нельзя переносить с Render на открытый сервер.
В `docker-compose.yml` есть переменные production, но текущая публикация портов
и bind-mount исходников предназначены для разработки: файл не является готовой
production-инфраструктурой. Конфигурация будущего сервера зависит от выбранного
владельцами reverse proxy и в рамках этого изменения не создавалась.
