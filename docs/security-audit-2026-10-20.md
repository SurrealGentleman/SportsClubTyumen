## Объект и границы проверки

Проверен текущий FastAPI-проект: публичные страницы и заявки, вход и CRUD SQLAdmin,
SQLAlchemy-запросы, сессии и конфигурация. Выполнены анализ исходников,
воспроизводимые HTTP-проверки и тесты CAPTCHA.

HTTP-проверки выполнялись через ASGI TestClient и отдельную SQLite-базу в памяти.
Тестовые записи не попадали в рабочую PostgreSQL-базу. Публичный домен не был
предоставлен: TLS-сертификат, настройки reverse proxy/WAF и заголовки реального
хостинга не проверялись. Схема `https` в TestClient не означает проверку TLS.
Реальный SmartCaptcha проверен по документации; интеграционные тесты используют
подменённые ответы провайдера. Проверка настоящего виджета с рабочими ключами
ещё требуется.

## 1. Брутфорс

Файл: `app/admin/auth.py`, метод `AdminAuthentication.login`.

Подтверждённые факты:

- 12 последовательных неверных паролей вернули `400`, без `429`, задержки,
  блокировки или `Retry-After`.
- Сразу после них правильный пароль позволил войти: `302`.
- В коде нет счётчика попыток, лимита по IP/аккаунту или общего хранилища лимитов.
- Пароли хешируются Argon2. Для неизвестного пользователя также выполняется
  проверка фиктивного хеша. Это полезные меры, но не ограничение подбора.

Рекомендация: ограничить попытки одновременно по IP и нормализованному логину,
использовать задержки и временные ограничения, предусмотреть восстановление
доступа без постоянной блокировки аккаунта. Для нескольких процессов/серверов
нужно общее хранилище лимитов, например Redis, либо подходящий лимит на proxy/WAF.
Не доверять произвольному `X-Forwarded-For`; доверенные прокси задавать явно.
Конкретные пороги выбрать с учётом общего IP университетской сети.

Основание: [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

## 2. SQL-инъекции

Проверены `app/admin/auth.py`, `app/routers/pages.py`,
`app/services/registrations.py`, административный поиск SQLAdmin и экспорт заявок.
Пользовательские значения передаются в выражения SQLAlchemy, а не собираются
в SQL через конкатенацию. `pks` для экспорта проверяется и преобразуется в число.
SQL в Alembic относится к миграциям и не принимает значения из веб-форм.

Воспроизведено в отдельной тестовой базе:

- Логин `' OR '1'='1' --` с правильным паролем тестового администратора вернул
  `400`, доступа в админку не дал.
- ФИО `Robert'); DROP TABLE registrations;--` в корректной заявке сохранилось
  как строка. Таблица осталась доступна.
- Через событие SQLAlchemy `before_cursor_execute` подтверждено, что эта строка
  находилась в параметрах, а не в тексте SQL-команды.
- Та же SQL-подобная строка в поиске админки вернула `200`; поисковое условие
  также использовало связанный параметр.

Вывод: уязвимость не обнаружена в проверенных сценариях. Это не доказательство
невозможности любой SQL-инъекции, особенно после изменения запросов или расширений.
Сохранять параметризацию; не подставлять пользовательские строки в `text()`,
`ORDER BY`, имена таблиц или колонок без фиксированного списка допустимых значений.

Основание: [OWASP SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

## 3. CSRF

Подтверждённые факты:

- `RussianAdminForm` не включает CSRF, в форме создания вида спорта нет токена.
- В публичных формах регистрации также нет CSRF-токена.
- Сервер не проверяет `Origin`, `Referer` или `Sec-Fetch-Site`.
- POST создания вида спорта с действительной сессией, без токена,
  с `Origin: https://untrusted.example` и `Sec-Fetch-Site: cross-site`
  вернул `302` и создал тестовую запись.
- `GET /admin/logout` изменяет сессию: после него администратор вышел из системы.

Ограничение воспроизведения: TestClient отправляет cookie независимо от браузерного
SameSite. Поэтому успешный POST выше подтверждает отсутствие серверной проверки,
но сам по себе не доказывает такую же отправку cookie современным браузером.
Сессия имеет `HttpOnly`, подпись и `SameSite=Lax`, что ограничивает часть
межсайтовых POST. При этом Lax допускает cookie при переходе верхнего уровня
методом GET и не защищает от всех запросов с соседних поддоменов.

Рекомендация: внедрить CSRF-токены для изменяющих запросов админки и публичных форм,
привязать токены к сессии/защищённому cookie, добавить проверку источника запросов,
перевести выход на POST. Проверить также DELETE и административные действия.
CAPTCHA не является заменой CSRF-защиты.

Основание: [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## 4. Защита форм от спама — внесённые изменения

Файлы: `app/services/captcha.py`, `app/templates/_registration_captcha.html`,
обе формы регистрации и обработчик `submit_registration`.

- Обычный виджет SmartCaptcha добавлен в индивидуальную и командную заявку.
- Проверка обязательна на сервере до сохранения заявки.
- Пустой, слишком длинный или неоднозначный токен отклоняется.
- Результат принимается только при `status=ok` и совпадении `host` с текущим
  хостом, который также должен находиться в настроенном списке разрешённых хостов.
- Проверка выполняется при каждой отправке. Провайдер отвечает за одноразовость
  и срок действия токена; локального кеширования успешных проверок нет.
- Сетевой таймаут — 5 секунд, ответ ограничен 4096 байтами. Синхронный запрос
  вынесен в thread pool, чтобы не блокировать async-обработчик.
- При сбое, неожиданном ответе или отсутствии настройки заявка не сохраняется.
  Это осознанный выбор доступности: сбой капчи временно блокирует регистрацию.
- HTTP-редиректы запрещены. Серверный ключ передаётся только в теле POST
  на фиксированный HTTPS-адрес провайдера и не попадает в HTML.
- Сервер не отправляет ФИО, email, телефон или содержимое заявки провайдеру.
  Сам браузер отдельно обращается к сервису виджета.

Состояние настройки на момент проверки: `CAPTCHA_ENABLED=true`, `captcha_ready=false`.
Ключи и разрешённые хосты ещё не заданы. Отправка заявок блокируется как через
страницу, так и прямым POST. Нельзя считать реальный виджет активированным.

### Включение SmartCaptcha

1. Создать капчу в Yandex Cloud и настроить допустимые домены.
2. Задать в `.env` и в окружении хостинга:

   ```dotenv
   CAPTCHA_ENABLED=true
   SMARTCAPTCHA_CLIENT_KEY=ysc1_...
   SMARTCAPTCHA_SERVER_KEY=ysc2_...
   SMARTCAPTCHA_ALLOWED_HOSTS=example.ru,www.example.ru
   ```

   Указывать точные хосты без схемы и пути. Для нестандартного порта включить
   его, например `localhost:8000`. Заменить пример на фактический домен сайта.

3. Перезапустить приложение. В браузере пройти капчу, отправить заявку,
   проверить неуспешную отправку без токена и повторное использование токена.
4. Убедиться, что reverse proxy сохраняет исходный Host и что backend принимает
   запросы только с предусмотренными хостами. Глобальный TrustedHost/WAF в этой
   задаче не внедрялся.

`CAPTCHA_ENABLED=false` явно отключает защиту; это допустимо для локальных
офлайн-тестов, но не является исправлением отсутствующих рабочих ключей.
Серверный ключ нельзя коммитить или помещать в клиентский JavaScript.

Капча не ограничивает количество HTTP-запросов, работу парсера форм и обращения
к БД до проверки. Дополнительно нужны лимиты частоты/размера запросов и мониторинг.
Заполненные человеком или оплаченные злоумышленником задания также возможны.

Документация: [создание и подключение](https://yandex.cloud/ru/docs/smartcaptcha/quickstart),
[серверная валидация](https://yandex.cloud/ru/docs/smartcaptcha/concepts/validation).

## 5. Заголовки безопасности

В ответах главной страницы как для HTTP-, так и для HTTPS-scope TestClient,
а также `/admin/login`, `/api/v1/health`, страницы 404 и CSS-статики по HTTPS:

| Заголовок | Значение приложения | Рекомендация |
|---|---|---|
| Content-Security-Policy | Отсутствует | Построить политику загрузки ресурсов и защиты от встраивания |
| Strict-Transport-Security | Отсутствует | Выдавать по HTTPS после проверки TLS и перенаправления с HTTP |
| X-Content-Type-Options | Отсутствует | `nosniff` |
| X-Frame-Options | Отсутствует | `DENY`, если сайт не требуется встраивать |

Для CSP учесть Bootstrap с jsDelivr, виджет SmartCaptcha, inline-style фона,
а также inline-инициализацию компонентов SQLAdmin. Простое `default-src 'self'`
может сломать интерфейс. Нужны подходящие разрешённые источники, nonce/хеши для
скриптов и проверка всех основных страниц. Начать можно с Report-Only,
после устранения нарушений включить принудительную политику.

Для запрета встраивания использовать также `frame-ancestors 'none'`,
для ограничения объектов — `object-src 'none'`, базового URL — `base-uri 'self'`,
отправки форм — `form-action 'self'`. Значения следует согласовать с архитектурой.

HSTS имеет смысл только при реальном HTTPS. Не включать автоматически
`includeSubDomains` и `preload`, пока не подтверждена готовность всех поддоменов.
Проверять заголовки также на ошибках, редиректах и страницах админки.

Основание: [OWASP HTTP Headers](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html),
[OWASP CSP](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html).

## Дополнительные наблюдения по настройкам

- В текущей локальной конфигурации `APP_DEBUG=false`.
- `SECRET_KEY` не равен стандартным заглушкам. Его значение не выводилось,
  оценка энтропии не проводилась.
- `SESSION_COOKIE_SECURE=false`. При публикации по HTTPS необходимо включить
  Secure-cookie и корректно настроить доверие к proxy-заголовкам.

## Воспроизведение и приоритеты

Результаты проверки на этой версии: 129 тестов прошли, включая 30 тестов CAPTCHA;
`ruff check .` и `git diff --check` завершились без ошибок. Audit-скрипт подтвердил
наблюдения из таблицы выше, включая поиск админки и заголовки разных типов ответов.

Команды из корня проекта с установленными dev-зависимостями:

```powershell
poetry run python -m scripts.security_audit
poetry run pytest tests/test_captcha.py
poetry run pytest
poetry run ruff check .
```

Audit-скрипт печатает JSON с наблюдениями, не выводит ключи или реальные заявки.
Для SQL-сценария он временно отключает капчу только внутри своего изолированного
процесса. Тесты CAPTCHA подменяют сетевые ответы и не используют реальный сервис.

Порядок дальнейших исправлений:

1. Ограничить попытки входа; внедрить CSRF в админке и изменить GET-выход.
2. Настроить рабочие ключи SmartCaptcha, лимиты запросов и HTTPS/Secure-cookie.
3. Настроить security headers с проверкой совместимости CSP.
4. Повторить проверку на фактическом домене после развёртывания.
