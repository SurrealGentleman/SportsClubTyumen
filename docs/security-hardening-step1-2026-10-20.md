## Что изменено

### Ограничение попыток входа

До проверки пароля резервируется попытка в общей PostgreSQL-таблице
`admin_login_attempts`. Атомарный UPSERT исключает превышение лимита при
параллельных запросах и нескольких процессах. SQLite поддерживается для тестов.
Перезапуск приложения, смена cookie или IP не сбрасывают ограничение логина.

По умолчанию разрешены 5 попыток на логин и 30 с одного IP за 900 секунд.
Окно начинается с первой попытки; после истечения счётчик обновляется.
Учитываются все попытки, в том числе успешные, неизвестные и отключённые логины.
Вход с правильным паролем также запрещён при исчерпанном лимите.
Ответ: HTTP 429, русский текст и заголовок `Retry-After` в секундах.
Заблокированные запросы не запускают дорогую проверку Argon2.
Хеширование пароля и операции счётчика вынесены из асинхронного цикла в threadpool.

Настройки в `.env` (также передаются в Docker Compose):

```env
ADMIN_LOGIN_ACCOUNT_LIMIT=5
ADMIN_LOGIN_IP_LIMIT=30
ADMIN_LOGIN_WINDOW_SECONDS=900
```

Ключи счётчиков — HMAC-SHA256 от IP/логина с секретом приложения, а не открытые
адреса или логины. Просроченные записи вероятностно удаляются отдельной транзакцией
примерно в 1% запросов входа. При отсутствии запросов они остаются до следующей
очистки. Смену `SECRET_KEY` счётчики не переживают: меняются ключи HMAC.
Не меняйте секрет как способ штатной разблокировки.

IP берётся из `request.client.host`, а не из произвольного `X-Forwarded-For`.
Если приложение за reverse proxy, настройте Uvicorn на доверие forwarded-заголовкам
только от адресов своего proxy и закройте прямой доступ к приложению. Иначе все
пользователи могут учитываться как один IP либо атакующий сможет подменять адрес.

Ограничение по логину позволяет временно заблокировать известного администратора
чужими попытками. Это осознанный компромисс против распределённого перебора;
постоянной блокировки нет. Для production полезны VPN/IP allowlist, MFA и лимиты
на reverse proxy: приложение само по себе не защищает от объёмного DDoS.

### CSRF в админке

Все небезопасные методы внутри SQLAdmin (`POST`, `PUT`, `PATCH`, `DELETE` и прочие,
кроме `GET`, `HEAD`, `OPTIONS`) проверяются единым middleware после SessionMiddleware.
В том числе защищены вход, создание, редактирование, удаление, импорт и выход.

Случайный 256-битный токен привязан к подписанной сессии. Обычные формы передают
`csrf_token`, AJAX — `X-CSRF-Token`. Токен из query string не принимается.
Сравнение выполняется за постоянное время. При успешном входе и выходе сессия
очищается, поэтому старая пара сессия/токен перестаёт использоваться браузером.
Это не серверный отзыв ранее украденной подписанной cookie: такие cookie остаются
действительными до истечения срока; это отдельное ограничение текущих сессий.

Дополнительно проверяются `Origin`, а при его отсутствии `Referer`, если они есть,
и `Sec-Fetch-Site: cross-site`. Отсутствие этих заголовков не отменяет токен.
Домен, схема и порт должны совпадать с URL запроса. За HTTPS-proxy важна правильная
передача схемы от доверенного proxy, иначе легитимные запросы получат 403.
CSRF-токены не отправляются JavaScript-кодом на посторонние origin.
Встроенный CSV-импорт через `fetch` и удаление через jQuery получают заголовок.

Ошибочный, чужой или отсутствующий токен приводит к HTTP 403 с предложением
обновить страницу, до изменения данных. Обычные HTML-формы работают без JavaScript;
проверка формы буферизует не более 1 МиБ тела, затем возвращает 413.
Административные ответы помечаются `Cache-Control: no-store`.

### Выход

Кнопка «Выход» отправляет POST с токеном. GET и HEAD `/admin/logout` возвращают
405 и не очищают сессию. POST без токена возвращает 403; с правильным — очищает
сессию и перенаправляет на страницу входа.

## Применение и проверка

Перед запуском обновлённого приложения выполните:

```powershell
poetry run alembic upgrade head
```

Новая миграция `20261020_05` добавляет только таблицу счётчиков и её индекс.
Существующие соревнования, заявки и администраторы не меняются. Без миграции
вход не работает: отсутствие таблицы намеренно не обходит ограничение.
Перезапустите приложение. Для HTTPS включите `SESSION_COOKIE_SECURE=true`.

```powershell
poetry run pytest
poetry run ruff check .
poetry run python -m scripts.security_audit
```

Автотесты проверяют: лимит логина при смене IP и сессии, лимит IP при смене логинов
и поддельном forwarded-заголовке, разблокировку по времени, параллельные независимые
экземпляры ограничителя, запрет CSRF-обходов, multipart-создание, AJAX-удаление,
ротацию токена, GET/HEAD/POST-выход. Аудит выполняется на временной SQLite-базе;
рабочие данные не используются. Production TLS/proxy и PostgreSQL-конкурентность
не подтверждаются тестами SQLite и требуют проверки на стенде.

## Зафиксированный результат повторной проверки

- Полный набор: **160 тестов пройдено**, включая 31 новый тест безопасности админки.
- `ruff check .`, `ruff format . --check`, `docker compose config --quiet` — успешно.
- SQL новой миграции для PostgreSQL успешно сгенерирован (`alembic upgrade head --sql`).
  Миграция в рабочую БД в рамках проверки не применялась.
- Локальный аудит: первые 5 неверных попыток — 400, последующие — 429;
  верный пароль после исчерпания лимита также получает 429 и `Retry-After`.
- CSRF: без токена — 403; запрос с постороннего origin даже с токеном — 403;
  новых записей после этих запросов нет.
- GET-выход — 405, сессия сохраняется; POST с токеном — 302, сессия очищается.
- Повторные проверки SQL-инъекций в логине, поиске и заявке нарушений не выявили.

## Оставшиеся задачи

CSRF для публичных заявок, security headers, MFA/серверный отзыв сессий, внешние
лимиты нагрузки и production-настройки HTTPS/proxy остаются отдельными задачами.
Настройка настоящих ключей SmartCaptcha и заполнение юридических документов
по-прежнему необходимы до публичного запуска.

Подход основан на рекомендациях OWASP:
[защита от CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html),
[ограничение входа](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
