# Security headers и совместимость CSP — 26 октября 2026

## Настройка

Общий ASGI-слой оборачивает также обработчик необработанных ошибок. Заголовки
добавляются к HTML, JSON, статическим ресурсам, выгрузкам, перенаправлениям,
ошибкам приложения, отказам CSRF и превышению лимитов. Сервер/балансировщик может
возвращать собственные ответы до приложения — их нужно проверять отдельно.

| Заголовок | Значение / условие |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `X-XSS-Protection` | `0`, устаревший браузерный фильтр отключён |
| `Strict-Transport-Security` | `max-age=31536000`, только HTTPS при Render/production |
| `Content-Security-Policy` | Профиль в зависимости от страницы |

HSTS перенесён в общий слой без изменения срока. На локальном HTTP он отсутствует;
`includeSubDomains` и `preload` намеренно не включены. На страницах с документацией
API задаётся `Cache-Control: no-store`, чтобы HTML и CSP с nonce не расходились.

COEP/CORP и COOP здесь не включаются: дополнительная изоляция без отдельной
проверки способна нарушить сторонние iframe/ресурсы. CORS глобально не открывается.

## Политики CSP

Центральная настройка: `app/core/security_headers.py`.

Общие ограничения: `default-src 'none'`, `object-src 'none'`, `base-uri 'self'`,
`frame-ancestors 'none'`, `form-action 'self'`, `script-src-attr 'none'`.
Таким образом, разрешение встраивать CAPTCHA в сайт не разрешает встраивать
сам сайт или админку в посторонний iframe.

- Публичные страницы: свои скрипты и точный URL Bootstrap 5.3.8 на jsDelivr.
  Исходные SRI-хеши Bootstrap сохранены.
- Админка: скрипты только со своего origin. Скрипт уведомлений SQLAdmin вынесен
  из inline-шаблона в `app/static/js/admin-flash.js`, уведомления не отключены.
  CAPTCHA и CDN публичных страниц админке не разрешаются.
- Swagger, OAuth redirect и ReDoc: отдельный профиль для их CDN, шрифтов и
  логотипов. Только доверенные inline-инициализаторы, генерируемые FastAPI,
  получают случайный nonce на каждый ответ. Пользовательское HTML-содержимое
  автоматически nonce не получает. Ненонцированные inline-скрипты блокируются.
- Формы регистрации с настроенной и включённой CAPTCHA: добавлены точные origin
  `smartcaptcha.cloud.yandex.ru` и `smartcaptcha.yandexcloud.net` для скриптов,
  iframe, изображений и соединений. Не разрешены все `*.yandex.ru` или все HTTPS-источники.

`unsafe-eval` не разрешён ни в одном профиле. Для **стилей**, не скриптов,
сохранён `unsafe-inline`: Bootstrap/Tabler/Select2/Flatpickr используют динамические
стили, а оформление бренда — CSS-переменную в атрибуте body. Это компромисс
совместимости; текущая политика не является строгой CSP для CSS.
Включение новых SQLAdmin rich-text редакторов требует повторной проверки:
их inline-инициализаторы сейчас не разрешены автоматически.

## Режимы и SmartCaptcha

```env
CSP_REPORT_ONLY=false
CSP_CAPTCHA_REPORT_ONLY=true
```

По умолчанию публичные страницы без виджета, админка и документация работают
с **принудительной CSP**. Для форм, на которых действительно настроена CAPTCHA,
полная ресурсная политика пока отправляется как `Content-Security-Policy-Report-Only`:
рабочие ключи ещё не созданы, поэтому совместимость настоящего задания провайдера
не подтверждена. В этом режиме ресурсные нарушения регистрируются браузером,
**но не блокируются**. Одновременно действует ограниченная принудительная политика
для `base-uri`, `object-src`, `frame-ancestors` и `form-action`.

После создания ключей на Render нужно:

1. Пройти CAPTCHA в формах обоих типов, включая дополнительное задание и повтор
   после ошибки формы; проверить Console и Network на CSP-нарушения.
2. Если провайдер использует дополнительные ресурсы, добавить только необходимые
   точные источники в соответствующие директивы CAPTCHA-профиля.
3. Установить `CSP_CAPTCHA_REPORT_ONLY=false`, выполнить redeploy и повторить
   проверку прохождения/отправки обеих форм. Убедиться, что на них присутствует
   полный `Content-Security-Policy`, а Report-Only отсутствует.

`CSP_REPORT_ONLY=true` — временный диагностический режим для всего сайта, а не
рекомендуемая production-настройка. Он также оставляет базовую принудительную
защиту от iframe/объектов/посторонней отправки форм.
Серверного сборщика отчётов нет: сообщения смотрят в браузере. Сбор URL/данных
нарушений во внешнюю систему без отдельного решения не добавлялся.

## Что проверено

Итоговый прогон: **202 теста пройдены**, включая 6 браузерных сценариев Chrome.
`ruff check .`, `ruff format . --check`, `docker compose config --quiet`
и повторный локальный аудит выполнены успешно.

Изолированные HTTP-тесты проверяют заголовки, профили, ошибки, nonce и отсутствие
inline-скриптов в текущих формах SQLAdmin. Профиль настоящего HTML SmartCaptcha
проверен на согласованность с URL подключаемого скрипта, но не на прохождение
реальной капчи.

Есть opt-in браузерная проверка в установленном Chrome, без новых зависимостей:

```powershell
$env:RUN_CSP_BROWSER='1'
poetry run pytest tests/test_csp_browser.py -q -s
Remove-Item Env:RUN_CSP_BROWSER
```

Она запускает отдельный headless-профиль Chrome, временный loopback HTTP-сервер
и приложение с SQLite в памяти. Рабочая БД и профиль Chrome пользователя не
используются. Из внешней сети загружаются публичные CDN-ресурсы Bootstrap/API docs.
Проверяются главная, добавление участника команды, вход и форма соревнования
в админке, загрузка Select2/Flatpickr/Tabler, Swagger и ReDoc. Специально вставленный
тестовый inline-скрипт должен быть заблокирован, других CSP-нарушений быть не должно.

Проверка в браузере выявила внешний логотип ReDoc; разрешение добавлено только
для его конкретного URL в профиле API docs. Ни админка, ни остальные страницы
это разрешение не получают.

После развёртывания отдельно проверьте ответы Render, включая его собственные
ошибки, 404, 429 и админку. Изменения в балансировщике/консоли Render здесь не
выполнялись. Для этих изменений новая миграция БД не нужна.
